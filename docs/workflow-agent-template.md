# 通用代理推进模板

本模板只定义如何使用已有工作流，不提供授权，不自动创建定时任务。为实际宿主配置真实 workflowId 和 actor。用户已明确要求定时跟进时，可通过宿主原生自动化接口将下列逻辑绑定到指定总控；不得手写未经验证的通知控制标签。

## 首次接入

1. 根据当前用户目标确认参与角色、动作、资源范围、完成条件和预算；已有明确授权可直接使用，不重复询问。
2. 通过 `workflow create` 创建稳定工作流 ID；初始 observe。
3. 按明确事项分别 add，绑定实际查询确认的会话。不要把多个待办合成一个会话状态，也不要猜测旧任务所属关系。
4. 将真实授权记录引用登记为 policy。assist 模式再为确切事项修订登记 approve。managed 只允许 policy 覆盖的动作，不自动获得发布或部署权限。

## 每次被唤醒时

使用实际本地入口执行 `dshq workflow next <workflowId> --json`，再按需读取 `workflow notices`。如果需要从 DSH 同步原始消息，执行一次有界 poll 并核对 complete/各绑定错误。纯采集可由独立本地程序调度，模型不必参与每轮检查；本模板本身不提供事件唤醒能力。

- 有 ready 项：核实版本、资源与授权，claim 后执行已有宿主能力范围内的工作。必要时使用 send，必须保存并复用 operationId；发送不确定先 reconcile，不换 ID 绕过。
- 有未决 effect：优先对账。不能因为暂无新通知而忽略。
- waiting：等待对应事项的新修订/输入，不重复执行旧工作。新 source 事件要显式关联 workItem ID/revision/绑定 epoch。
- blocked：说明具体原因；在现有授权内解决后显式 resume。需要新范围/权限时交用户裁决。
- readyCount=0、无未决 effect、无需要处理的新事件：结束当前检查，不生成例行重复提醒。

通知已读与工作完成分离。mark-notices 只在事件已正确分类后使用；待办仍由 next 返回。未经分类的自然语言 observation 不能直接当作完成结论；如实际包含独立新事项，先核对并 add，或以 event 关联现有事项，再标记通知。

## 收尾和恢复

先实际执行领域验证，再 finish accepted/needs_changes/failed 并引用准确证据版本。证据字段的存在不证明内容真实。handoff 型事项还需要发送本修订结论的回执，不能引用初始派发回执。

run/claimId 过期、授权或绑定变更时停止使用旧句柄，重新读取状态。进程丢失后的旧发送可能已生效，不盲目重发。收到新修复回执只推进对应事项，不重派整个工作流。

总控交接须显式 handoff；新总控先 observe，再依据真实授权登记 policy。不要继承旧会话的未经确认权限。已有临时脚本、检查点和自动化只能在另行迁移时逐项核验，不自动接管。
